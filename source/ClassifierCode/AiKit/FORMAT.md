# Формат профиля классификатора

Профиль — один JSON-файл `*.classifier.json`. По нему плагин «Код по классификатору» определяет для каждого элемента модели позицию классификатора и записывает её код и описание в параметры элемента. Здесь описано каждое поле и то, как движок их использует. Машинная схема — `profile.schema.json`, проверка — `kit\check\check.exe validate`.

Ключи JSON пишутся в camelCase. Пустые списки и словари можно не писать. Неизвестное поле — ошибка чтения.

## Как движок получает код

Для элемента в выбранном **режиме** (разделе модели: отопление, водопровод, электрика…):

1. **Исключения** (`exceptions`) — правила объекта, раньше всего остального. Исключение может сразу дать позицию (`position`), пропустить элемент (`skip`) или заранее задать тип и/или раздел.
2. **Тип элемента** — набор правил режима (`modes[].typeRules` → `ruleSets`). Тип — «что это»: труба, арматура, КИП, изоляция, оборудование.
3. **Раздел** — правила раздела режима (`modes[].disciplineRules`), иначе `defaultDiscipline`. Раздел — «к какой системе относится»: водопровод, канализация, отопление, теплоснабжение.
4. **Позиция** — таблица режима (`modes[].table` → `tables`): строка «раздел + тип → позиция». Нет точной строки — замены типа (`fallbacks`) по порядку, затем строка с разделом `*`.

Нет типа, раздела или строки таблицы — элемент «не классифицирован» с причиной. Тип и раздел каждого элемента считаются один раз: их наследуют вложенные семейства (`inherit: "parent"`) и изоляция (`inherit: "host"`).

## Шапка

| Поле | Что это |
|---|---|
| `schemaVersion` | Версия формата, сейчас `1`. |
| `id` | GUID профиля. У профиля нового объекта — **новый** GUID, иначе он заменит чужой профиль в библиотеке. |
| `name` | Название, которое видят в окне запуска: обычно заказчик и объект. |
| `description` | Описание для людей. |
| `author` | Кто собрал. |
| `version` | Редакция профиля, например `1.0`. Модель помнит, какой редакцией её заполняли. |
| `fileNamePatterns` | Шаблоны имени файла модели: если имя подходит, окно запуска выбирает этот профиль само. |
| `outputs` | Куда писать: список полей `field` → `parameter`. |
| `categories` | Категории Revit (`OST_…`), элементы которых обрабатываются и к которым привязываются параметры. |

### outputs

| Поле | Что это |
|---|---|
| `field` | `code` — код позиции, `description` — описание, или имя дополнительной колонки позиции (`extra`). |
| `parameter` | Имя параметра Revit. Пустое — поле не пишется. Поле `code` обязательно. |
| `guid` | GUID общего параметра: по нему параметр ищется однозначно и подгружается из ФОП. |

## Классификатор

`positions` — позиции заказчика. **Только из таблицы заказчика** (служебная `999` «Не учитывать» допустима).

| Поле | Что это |
|---|---|
| `code` | Код, например `04.05.01.07.04.01`. |
| `description` | Описание, как в таблице. |
| `extra` | Дополнительные колонки таблицы (`{"Ед. изм.": "шт."}`) — пишутся, если для них есть `outputs`. |

`disciplines` — разделы, `types` — типы элементов. У обоих:

| Поле | Что это |
|---|---|
| `key` | Ключ латиницей: на него ссылаются правила и таблица (`water`, `pipe`). |
| `title` | Название для людей и отчёта. |
| `position` | Код позиции раздела (`04.05.01.01`) — для отчёта и подсказок. |

## Тексты

`texts` — именованные источники текста. Правила проверяют не элемент целиком, а такой текст. Источник склеивает части через ` | `.

| Поле | Что это |
|---|---|
| `parts` | Части по порядку (список ниже). |
| `lowercase` | Привести к нижнему регистру. |
| `normalize` | Верхний регистр и латинские буквы-двойники → кириллица (`B1` латиницей = `В1`). Нужно для шифров систем. |
| `fallback` | Имя другого источника, который читается, если все части пусты. |

Части:

- `instance.name` — имя экземпляра; `type.family` — семейство; `type.name` — имя типа; `familyType` — «семейство | тип» (если типа нет — имя экземпляра);
- `instance.comments`, `type.comments` — комментарии;
- `systems` — системы элемента: имя системы, имя типа системы, сокращение (у арматуры и фитингов — систем, к которым они подключены);
- `workset` — рабочий набор; `document.title` — имя модели;
- `instance:Имя параметра`, `type:Имя параметра`, `instanceOrType:Имя параметра` (экземпляр, а если пуст — тип);
- `firstStringMatching:шаблон` — первое строковое значение параметра экземпляра, затем типа, подходящее под шаблон;
- `text:имя` — другой именованный источник.

Пример из основы:

```json
"texts": {
  "primaryName": { "parts": ["instanceOrType:ADSK_Наименование"], "lowercase": true },
  "fullName": { "parts": ["instance.name", "instance:ADSK_Наименование", "type.family", "type.name", "type:ADSK_Наименование"], "lowercase": true },
  "system": { "parts": ["systems", "instance:ADSK_Имя системы", "instance:ADSK_Система"], "normalize": true }
}
```

## Шаблоны

Шаблон — строка, которая ищется в тексте без учёта регистра.

| Шаблон | Значит | Совпадёт с |
|---|---|---|
| `трап` | слово, начинающееся с «трап» | «Трап ТП-42», «трапы» |
| `трап*` | то же (звёздочка в конце ничего не меняет) | |
| `*изоляц` | где угодно, хоть внутри слова | «теплоизоляция» |
| `=пк` | слово целиком | «ПК-1», но не «пкс» |
| `шкаф пожарн` | слова подряд; у всех, кроме последнего, допускается окончание | «шкафы пожарные» |
| `#В1` | шифр системы: перед ним не буква, после не цифра | «В1», «1В1», но не «В11», не «ОВ1» |
| `#!В1` | шифр, перед которым и не цифра | «В1», но не «1В1» |
| `re:…` | регулярное выражение .NET как есть | |
| `@имя` | любой шаблон набора `patternSets.имя` | |

`patternSets` — именованные наборы шаблонов, чтобы не повторять списки: `"trap": ["трап", "*трап"]`, а в словаре — `"@trap"`. Шаблон, проверяющийся дольше 5 с, считается ошибкой элемента — упростите его.

## Словари

`dictionaries` — «текст → результат». Словарь применяется к тексту шага или условия.

| Поле | Что это |
|---|---|
| `mode` | `first` — первая запись сверху, у которой совпал шаблон; `earliest` — совпадение, стоящее в тексте раньше (при равенстве — запись выше); `lastToken` — текст режется по `separators`, токены проверяются с конца на точное равенство (шифр подсистемы в «ШФТ-СОБ-АУПС»). |
| `normalize` | Нормализовать текст перед поиском (как у текстов). |
| `separators` | Регулярка разделителей для `lastToken`, например `[-_.\\s]+`. |
| `entries` | Записи по порядку. |

Запись словаря:

| Поле | Что это |
|---|---|
| `result` | Что дать (ниже). |
| `patterns` | Шаблоны; для `lastToken` — точные токены. |
| `when` | Условия записи (все через И): запись участвует, только если они выполнены. |

### Результат

| Поле | Что это |
|---|---|
| `discipline` | Ключ раздела. |
| `type` | Ключ типа. |
| `position` | Код позиции — сразу итог, без таблицы. |
| `skip` | Пропустить элемент, текст — причина в отчёте; `{match}` заменяется совпавшим текстом. |
| `pipe`, `air` | Разные результаты для элементов трубопроводов и воздуховодов (сети определяются по подключению). |

В результате задаётся одно: `discipline`, `type`, `position` или `skip` — либо `pipe` и/или `air` с ними внутри.

## Правила

`ruleSets` — именованные наборы правил типа (на них ссылается `modes[].typeRules`). Правила раздела лежат прямо в режиме (`disciplineRules`), исключения — в `exceptions`. Правила проверяются сверху вниз.

| Поле | Что это |
|---|---|
| `title` | Название — видно в трассе `explain`. |
| `when` | Условия (все через И). Не выполнены — следующее правило. |
| `steps` | Шаги по порядку; первый, давший результат, решает. |
| `allow` | Допустимые результаты шагов этого правила. |
| `refine` | Уточнения результата правила. |
| `default` | Результат, если ни один шаг ничего не дал. |
| `fallthrough` | Шаги ничего не дали и `default` нет: `true` — перейти к следующему правилу, `false` (по умолчанию) — остановиться **без результата**. |

Шаг:

| Поле | Что это |
|---|---|
| `dictionary` + `source` | Применить словарь к источнику `texts`. |
| `sources` | Несколько источников, склеенных через ` | `, вместо `source`. |
| `inherit` | `parent` — взять тип/раздел родительского семейства; `host` — изолируемого элемента (для изоляции). |
| `onlyIf` | Для `inherit`: брать, только если у родителя/хоста такой результат. |
| `fixed` | Готовый результат. |
| `refine` | Уточнения результата этого шага. |

`allow`: `values` — список допустимых ключей; `otherwise` — `drop` (шаг считается не давшим ничего, проверяется следующий) или ключ, которым заменить недопустимый. Пропуск (`skip`) список не ограничивает.

Уточнение (`refine`): `when` — условия, `to` — результат вместо найденного. Срабатывает первое подходящее.

### Условия

Каждое условие проверяет одно; `not: true` — наоборот.

| Поле | Что это |
|---|---|
| `not` | Инверсия. |
| `category` | Категория элемента — одна из списка. |
| `domain` | `pipe`, `air` или `other` — сеть элемента. |
| `mode` | Текущий режим — один из списка. |
| `type` | Тип элемента — один из списка (на стадии раздела — найденный тип; в уточнениях стадии типа — только что найденный). |
| `source` | Источник текста; `$source` — текст, на котором сработал шаг (только в уточнениях). |
| `matches` | Вместе с `source`: текст подходит под шаблон. |
| `dictionary` | Вместе с `source`: словарь что-то дал. |
| `gives` | С `dictionary`: дал один из этих ключей (`skip` — пропуск). |
| `givesNothing` | С `dictionary`: ничего не дал. |

## Таблицы и режимы

`tables` — таблицы «раздел + тип → позиция».

| Поле | Что это |
|---|---|
| `rows` | Строки: `discipline` (ключ или `*` — любой раздел), `type`, `position`. |
| `fallbacks` | Тип → замены по порядку, если строки для типа в разделе нет: `"kip": ["armature"]` — КИП без своей строки идёт как арматура. Замены не транзитивны. |

`modes` — разделы модели, из которых выбирают в окне запуска.

| Поле | Что это |
|---|---|
| `key` | Ключ режима. |
| `title` | Название в окне. |
| `hint` | Подсказка под выбором (какие системы куда). |
| `reportMode` | Как режим назван в отчёте. |
| `fileTokens` | Шифры раздела в имени файла: имя режется по `-_. ()`, токены проверяются с конца (`ШФТ-СОБ-1-ОВО` → `ОВО`). |
| `unconnectedAsAir` | Неподключённые элементы считать воздуховодами (для вентиляции). |
| `typeRules` | Имя набора в `ruleSets`. |
| `disciplineRules` | Правила раздела. |
| `defaultDiscipline` | Раздел, если правила ничего не дали. |
| `table` | Имя таблицы в `tables`. |

## Как сделать

**Новый объект из основы.** Скопируйте основу, поменяйте `id` на новый GUID, `name`, `version`, `fileNamePatterns`, `fileTokens` режимов. Позиции — из таблицы заказчика; `position` у разделов и строки таблиц — на коды заказчика.

**Новый раздел** (например, ИТП 04.05.01.12):

```json
"disciplines": [ { "key": "itp", "title": "ИТП/ЦТП", "position": "04.05.01.12" } ],
"tables": { "ios": { "rows": [
  { "discipline": "itp", "type": "equipment", "position": "04.05.01.12.01" },
  { "discipline": "itp", "type": "pipe", "position": "04.05.01.12.02.01" }
] } }
```

и правило, которое его даёт — запись в словаре раздела по шифру системы и/или правило в `disciplineRules` нужного режима:

```json
{ "result": { "discipline": "itp" }, "patterns": ["#ИТП", "*тепловой пункт"] }
```

Если раздел живёт в отдельной модели — заведите режим с его `fileTokens`.

**Новый шифр системы.** Добавьте шаблон `#Т31` в набор `patternSets`, на который ссылается словарь раздела (например, `heatingSystem_heating`). Шифры берите из `check summary` (`work\summary\systems.tsv`), а не по памяти.

**Новое слово типа.** Добавьте шаблон в набор типа (`patternSets.kip`) или запись в словарь типов. Проверьте `explain` на элементе с этим наименованием.

**Исключение** — когда правило объекта важнее распознавания: всё с «Гильза» в наименовании — как трубы, задания на отверстия — пропустить:

```json
"exceptions": [
  { "title": "Задания на отверстия", "when": [ { "source": "fullName", "matches": "*отверсти" } ], "default": { "skip": "задание на отверстие" } }
]
```

У исключения обязательно есть условия: без них оно сработало бы на всех элементах.
